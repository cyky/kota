# WONTFIX — 39 — `--no-history`: a neutral snapshot commit instead of the project's last commit

Status: wontfix
Category: enhancement

## Parent

`.scratch/agent-sandbox/PRD.md`

## What to build

A `--no-history` **Session** still shows the project's last commit: `git log` in the **No-history copy** lists it with its message, author, email, date and hash. That is history, and it can say more than the user wants the agent to see (a message naming what was removed, an email address). The flag's name suggests no commits from the project at all, which is how it reads when tried.

Replace that commit in the copy with a **neutral snapshot**: a root commit with the same tree, a fixed author and committer (`kota <kota@localhost>`), a fixed date, and a fixed message saying it is a snapshot without history. Nothing in the copy then names the original commit, and the agent's commits build on the snapshot.

Bringing the work back (issue 31) changes with it. The original doesn't have the snapshot, so the bundle's prerequisite and the ancestry check can't use it as they do now:

1. **Record the base.** The clone container prints the original `HEAD` it cloned, and that commit, not the original's `HEAD` when the **Session** ends, is the base of the **Returned branch**.
2. **Make the snapshot in both places.** The snapshot is built from the base's tree with the fixed metadata, so the same commit (same hash) can be made in the original's git dir during the return. The return checks the hash matches the copy's snapshot, and refuses otherwise (copy kept).
3. **Fetch** the bundle (prerequisite: the snapshot) into a temporary ref, as now, and check it descends from the snapshot (otherwise "history rewritten", as now).
4. **Re-parent** each commit from the snapshot to the tip onto the base, in order, with `git commit-tree`: same tree, author, committer and message; the snapshot parent becomes the base. The trees are unchanged, so there is nothing to merge. Merge commits keep their other parents, mapped.
5. Create the **Returned branch** at the re-parented tip as now, and remove the temporary ref. The returned commits have new hashes; the change report counts and names those.

The original commit object must not be readable in the copy: prune it after replacing the ref (the shallow file, the clone's pack), and check `git cat-file -e <original HEAD>` fails.

## Acceptance criteria

- [ ] In a `--no-history` **Session**, `git log` shows one commit, by `kota <kota@localhost>` with the fixed message and date, and no trace of the original commit's message, author, email, date or hash
- [ ] `git cat-file -e <original HEAD>` fails in the copy, and no `.git/shallow` remains
- [ ] The snapshot's tree is the original `HEAD`'s tree, and kota's config files still come from the original (issue 29)
- [ ] The agent's commits come back as the **Returned branch** on the base, with their trees, authors and messages unchanged
- [ ] A merge commit in the agent's work comes back with its parents mapped
- [ ] A history the agent rewrote (the tip doesn't descend from the snapshot) isn't brought back, as now
- [ ] The base is the original `HEAD` when the copy was made, even if the original moved during the **Session**
- [ ] A snapshot that can't be remade with the same hash in the original refuses the return and keeps the copy
- [ ] git still never runs on the host against the original or the copy; clone and return run in offline containers as now
- [ ] README and `CONTEXT.md` (**No-history copy**) say the copy has one neutral snapshot commit, not the project's last commit
- [ ] Tests use a fake HOME

## Comments

### 2026-10-18

Raised after trying `--no-history`: having the last commit in the copy's history is confusing, and its message, author and date leak information the agent doesn't need.

### 2026-10-18 (grilling, dropped)

> *This was generated by AI during a grilling session.*

Two decisions were reached before the issue was dropped: the copy would keep one neutral snapshot commit (not none), and the return would remake that commit in the original from the base's tree and check its hash, rather than bundling the whole tree.

Dropped because it doesn't solve the problem behind it. The need was a monorepo where old, unsanitized code and its history must be kept from the agent while it works on a new project in the same repository. A neutral snapshot hides only the last commit's metadata: the snapshot's tree still holds every file of the last commit, masked ones included (`git show HEAD:<path>`), as today's copy does. For that case, pointing kota at the new project's subdirectory already works: only that directory is mounted, the repository's `.git` is above it, so the agent sees no git history at all.

Instead, the README, flag help and startup line now say `--no-history` keeps the last commit (its files, message, author and date), that masked tracked files stay readable from it, and describe the subdirectory approach. Hiding paths from the snapshot itself would need the return to graft them back into every agent commit; file that only if the subdirectory approach falls short (for example, when the project needs code from elsewhere in the monorepo).
