## What to check

kota runs git on the host against the project in four places:

- `internal/mask/mask.go:254`: `git -C <project> ls-files -z`
- `internal/mask/mask.go:375`: `git -C <project> config --type=path --get core.hooksPath`
- `internal/mask/gitconfig.go:210`: `git -C <project> config --list --show-origin -z`
- `cmd/kota/gitEnv` (`main.go:943`): `git -C <project> config --get user.name` / `user.email`

The Change report and the No-history copy run git only in offline containers, because a repository's config and `.gitattributes` can name filters and an fsmonitor that git runs. These four run before a Session, on a repository the agent may have changed in an earlier one.

For each call: can anything the agent can write (repository config, `config.worktree`, includes, the index and its extensions, `.gitattributes`) make it run a program or read a path outside the project? Check with the git version kota supports, in a throwaway repo. Record the findings here, then decide whether each call moves into `offlinegit` (cost: one container start per call) or stays on the host with the reason written next to it.

## Acceptance criteria

- [x] `git config -f <file>` calls run with the working directory `/`, outside any repository

### 2026-10-19 (triage)

> *This was generated by AI during triage.*

There are seven host git calls in production code, not four. The other three:

- `git config -f <file> --get` (mask: reading one key from one config file, e.g. `extensions.worktreeConfig`, a submodule's `core.worktree`)
- `git config -f <file> -z` (mask/gitconfig: the entries of one config file, without includes)
- `git config --global --get core.excludesFile` (changereport): runs from `/` with `--global`, so it never reads the project. Safe as it is.

**Reproduced: host code execution** (git 2.55, throwaway repo in the scratchpad). In a Session the agent can write `.git/HEAD` (not protected) and files at the project root. It breaks `.git/HEAD` and plants `HEAD`, `objects/`, `refs/`, `index` and a `config` with `core.bare=false`, `core.worktree=<project>` and `core.fsmonitor=<program>`. Host `git -C <project>` then falls back to the root as a bare repository:

- `git -C <project> ls-files -z` ran the planted fsmonitor program. `mask.Plan` makes that call before every `run`, `shell`, `check` and `prep` of a project with a masked file (such as `.env`), with no prompt.
- `config --list --show-origin`, `config --get core.hooksPath` and `config --get user.name` all returned the planted values: kota would protect a hooks path of the agent's choosing, or none, and pass the agent's identity.

`docs/protections.md` already lists the bare-repository fallback as a limit for the user's own git; kota's own calls were not considered.

Both of these stopped the fallback in the reproduction: `-c safe.bareRepository=explicit` (git refuses the discovered bare repository), and an explicit `--git-dir=<project>/.git` (git fails with "not a git repository" instead of discovering). With the explicit git dir, a broken `.git` makes kota's calls fail, which `mask.Plan` already turns into a refused session.

Decided with the maintainer: harden kota's host calls; don't move them into offline containers, and don't change any git config (the user's or the project's).

## Agent Brief

**Category:** bug (security)
**Summary:** kota's host git calls against a project use an explicit git dir and refuse the bare-repository fallback and fsmonitor, so files the agent planted can't run a program on the host or feed kota false config.

**Current behavior:**
Before every `run`, `shell`, `check` and `prep`, kota runs git on the host against the project with `git -C <project> ...`: `ls-files -z` (tracked masked files), `config --get core.hooksPath`, `config --list --show-origin -z` (config origins for include and exec-reference protection), and `config --get user.name` / `user.email` (the identity passed into the Sandbox). It also runs `git config -f <file> ...` on single config files. All of them rely on git's repository discovery. When `.git/HEAD` is broken, discovery falls back to the project root as a bare repository, where the agent can plant `HEAD`, `objects/`, `refs/`, `index` and `config`. A planted `config` with `core.worktree` and `core.fsmonitor` makes `ls-files` run the agent's program on the host, and every config read returns the planted values.

**Desired behavior:**
- Every host git call against a project names the repository explicitly: `--git-dir=<project>/.git --work-tree=<project>`, plus `-c safe.bareRepository=explicit` and `-c core.fsmonitor=false`. None uses `-C <project>` discovery. Keep these in one place (a small helper), so a new host call gets them by default.
- `git config -f <file>` calls run with the working directory `/`, so no discovery reaches the project.
- When `.git` can't be read as a repository (broken `HEAD`, planted root bare-repository files), the calls fail and the session refuses before it starts, as `mask.Plan` errors do today. The error says `.git` in the project isn't a readable repository and that the agent may have changed it, so the user checks `.git/HEAD` and files at the project root before running git there.
- Each host git call has a comment saying why it may run on the host: it reads only, with discovery, bare repositories and fsmonitor off.
- No git config is written anywhere; the `-c` settings apply to kota's own git processes only.

**Key interfaces:**
- The mask planner's host git calls (tracked files, `core.hooksPath`, config origins and entries, single-key reads) and the session's git identity read: these get the hardened invocation.
- The global `core.excludesFile` read in the Change report: already safe (`--global`, from `/`); leave it, with a comment.
- Offline-container git (`offlinegit`) is unaffected.

**Acceptance criteria:**
- [ ] No host git call against a project relies on discovery: each passes `--git-dir=<project>/.git --work-tree=<project>`, `-c safe.bareRepository=explicit` and `-c core.fsmonitor=false`, through one helper
- [ ] `git config -f` calls run from `/`
- [ ] Test (no Docker, fake HOME and git config): with a broken `.git/HEAD` and a planted root `config` with `core.worktree` and `core.fsmonitor` pointing at a script that writes a marker, `mask.Plan` returns an error naming `.git`, and the marker is never written
- [ ] Test: with the same plant, the git identity read returns nothing from the planted `config`
- [ ] Test: a normal repository still plans as before (tracked masked files warned about, `core.hooksPath` protected, includes found), and a linked worktree or submodule `.git` file still works where it did
- [ ] `docs/protections.md`'s bare-repository limit says kota's own git calls don't fall back, and still recommends `git config --global safe.bareRepository explicit` for the user's own git
- [ ] `go test ./...` passes, and the Docker integration tests pass

**Out of scope:**
- Moving host git calls into offline containers.
- Changing the user's or the project's git config.
- Protecting the user's own host git from the planted files beyond the refusal and the docs.
- Protecting `.git/HEAD` itself in the Sandbox.

### 2026-10-19 (implementation)

> *This was generated by AI during implementation.*

New package `internal/hostgit`: `Command(project, args...)` and `ConfigFile(file, args...)`. Deviations and details:

- A project without `.git` runs `git -C <project>` with the same `-c` settings: the identity read can still find a repository above the project, which the agent can't write, while a bare repository planted at the project root is refused (`safe.bareRepository=explicit`). With `.git` (a directory, or a linked worktree's or submodule's `.git` file), git uses exactly that.
- `Command` runs in the project directory, so relative paths in git's output resolve as before. With an explicit git dir, git discovers nothing from there.
- `mask.Plan` checks the repository first (`rev-parse --git-dir`) and refuses with `<project>/.git isn't a readable git repository (<git's error>). It may have been changed in an earlier session: check .git/HEAD, and HEAD, config, objects and refs at the project root, before you run git there`.
- The global `core.excludesFile` read in the Change report stays as it was (from `/`, `--global`), with a comment.
- `docs/architecture.md` shows `hostgit`.

Tests (no Docker, fake HOME and git config):
- `TestPlanRefusesPlantedRepository`: the full plant with a masked `.env`; Plan refuses, naming `.git`, and the fsmonitor never runs. A control in the same test shows plain git runs it.
- `TestCommandRefusesPlant` (git and non-git project): `ls-files`, `status` and `rev-parse` fail, the fsmonitor never runs, and no config read returns a planted value.
- `TestCommandReadsRepositories`: normal repository, linked worktree, a subdirectory of a repository, and a non-git directory falling back to the global config.
- `TestGitEnvIgnoresPlantedRepository` and `TestConfigFileRunsOutsideRepositories`.

Verified: `go test ./...`, `go vet` (also with `GOOS=linux` and `-tags integration`), `gofmt`, and `go test -tags integration ./...` in every package.
